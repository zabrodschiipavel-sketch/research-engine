# ROADMAP — план развития research-engine

*This is the unedited, phase-by-phase build log — in Russian, the language the project was actually built and narrated in. For an English overview of the architecture and engineering highlights, see the [English section of README.md](README.md#english).*

## Видение

Из одноразового агента («промпт → отчёт») — в исследовательскую систему
с накапливаемым корпусом: каждый запуск обогащает локальную базу
источников, по которой можно искать и отвечать на вопросы (RAG) без
повторных походов во внешние API, а поверх — граф знаний (цитирования,
сущности, связи между работами).

## Принципы

- Минимум зависимостей: stdlib + SQLite; numpy и расширения — только
  когда без них никак.
- CPU-only friendly: эмбеддинги через локальный llama.cpp
  (`--embedding`) или бесплатные API; никаких тяжёлых ML-стеков.
- Бережём бюджеты API (Brave free 1 rps, CORE, DeepSeek) — локальный
  кэш обязателен.
- Всё состояние — один файл SQLite (`corpus.db`): просто бэкапить,
  просто смотреть глазами.

## Внеплановое: DeepSeek vs Gemini (2026-07-19)

Второй драйвер (`research_gemini.py`, Gemini 3.5 Flash через Interactions
API) появился раньше Фазы 4 — по прямому запросу, не по плану. Прогнали
обе модели на двух реальных темах из Фазы 2/3 (гибридный ретривал,
citation-graph retrieval) с одинаковым набором инструментов. Разбор —
[comparisons/2026-07-19-deepseek-vs-gemini/SUMMARY.md](comparisons/2026-07-19-deepseek-vs-gemini/SUMMARY.md).
Коротко: DeepSeek глубже и охотнее лезет в OpenAlex/CORE, но дороже и
медленнее; Gemini компактнее и в моменте бесплатен, но почти не трогал
специализированные научные инструменты и упирается в free-tier rate
limit быстрее. Встроенный `google_search` не взлетел без биллинга —
подробности там же.

Следом прогнали весь доступный зоопарк моделей Gemini (7 вариантов) —
сначала на одной теме, потом (после того как в `research_gemini.py`
починили обрезку текста ошибки до 300 символов) повторили на второй —
картина идентична на обеих, разбор в
[comparisons/2026-07-19-gemini-model-zoo/SUMMARY.md](comparisons/2026-07-19-gemini-model-zoo/SUMMARY.md).
Из семи реально отработали три, и все — Flash: `gemini-3.5-flash`,
`gemini-3.1-flash-lite`, `gemini-3-flash-preview`. Оба Pro-варианта
упёрлись в `429` на обеих темах — с полным текстом ошибки выяснилось,
что это не рейт-лимит, а буквально `limit: 0` на free tier для Pro,
подтверждено самим API. `gemini-2.5-flash`/`-flash-lite` сняты с
публичного доступа, `gemini-2.0-flash` стабильно валит `500` через
новый Interactions API (старое поколение с ним, похоже, несовместимо) —
оба факта не зависят от темы. Из рабочих младших моделей ни
`3.1-flash-lite`, ни `3-flash-preview` не позвали ни одного инструмента
ни на одной из двух тем — и на второй теме `3.1-flash-lite` поймана на
галлюцинированной ссылке (реальный DOI, но статья о совершенно другом).
Для research-агента вывод устойчивый: `gemini-3.5-flash` пока
единственный реально пригодный вариант в этой линейке на бесплатном
ключе — остальные Flash-варианты дешевле, но менее надёжны, не просто
компактнее.

## Фаза 1 — корпус (M; ключевая — всё дальнейшее стоит на ней) — done (2026-07-19)

`corpus.db` (SQLite, `corpus.py`):

- [x] `works` — работы из OpenAlex/CORE/Brave, дедуп по DOI/core_id/URL
      (свежие непустые поля побеждают старые при повторной встрече).
      **Известный пробел:** дедуп только по точным идентификаторам, без
      fuzzy-match по заголовку — если CORE не вернул DOI для записи,
      которая уже есть по OpenAlex, получится дубль-строка (наблюдал
      это на «An Analysis of Fusion Functions for Hybrid Retrieval» —
      DOI у OpenAlex-версии есть, у CORE-версии в ответе поиска не
      пришёл). Не чиню — не входило в объём фазы, fuzzy-дедуп заведёт
      риск ложного слияния разных работ.
- [x] `fulltexts` — кэш полных текстов CORE, `get_fulltext` сначала
      смотрит сюда (подтверждено: второй запрос того же core_id вернул
      `cached: true`, без похода в CORE API).
- [x] `runs` — пишет `trace.py` при старте/финише запуска (провайдер,
      модель, usage, раунды). Отдельную `tool_calls`-таблицу в SQLite
      не заводил — тот же смысл уже даёт `runs/<run_id>/tool_calls.jsonl`
      на диске, дублировать в БД не стал (не ради красоты).
- [x] FTS5-индекс (`works_fts`, `tokenize=unicode61`) по title/abstract/
      description/fulltext, ранжирование через `bm25()`. Риск из раздела
      «Риски» не подтвердился — FTS5 в этой сборке `sqlite3` (3.49.1)
      работает из коробки, включая кириллицу.

Новый инструмент агента `search_corpus` — в `TOOL_SPECS`, автоматически
доступен обоим драйверам. Промпт агента получает `CORPUS_HINT`
(«сначала проверь корпус») — работает: в тестовом прогоне модель сама
трижды дёрнула `search_corpus` первым делом.

**Сквозная проверка (реальная, не синтетика):** прогнал тему A через
`research.py` (DeepSeek) — корпус наполнился 48 работами (29 brave / 16
openalex / 3 core) + 1 закэшированный фултекст. Затем **отдельным
процессом**, через **другой драйвер** (`research_gemini.py`), с
**другой формулировкой** запроса — Gemini сам нашёл ту же статью через
`search_corpus` и получил её текст через `get_fulltext` с `cached: true`.
Корпус реально переживает между прогонами и между провайдерами — не
только в теории.

Заодно чинил реальный баг, не связанный с корпусом напрямую: `print()`
падал на кириллице в аргументах тул-коллов из-за не-UTF8 консоли
Windows (`sys.stdout.reconfigure` в обоих драйверах).

**Результат:** «RAG-лайт» без эмбеддингов уже работает — полнотекстовый
поиск по накопленному.

## Фаза 2 — RAG (M) — done (2026-07-19)

- [x] Чанкинг фултекстов (`chunking.py`): по абзацам (`\n\s*\n`),
      target 1500 / max 2200 символов, рекурсивный фолбэк по границам
      предложений для абзацев крупнее max. Без overlap — границы по
      абзацам и так сохраняют смысловые единицы. Offsets точные
      (проверено побайтово на реальном фултексте: 85 692 символа → 38
      чанков, все `text[start:end] == chunk.text`). На редких абзацах
      без знаков препинания (списки литературы, формулы) может
      перебрать max на ~15% — не чинил, не критично для эмбеддинга.
- [x] Эмбеддинги — выбрал **локальный путь**: `llama-server --embedding`
      + `nomic-embed-text-v1.5` (уже была скачана для LM Studio,
      768 измерений, мультиязычная). Gemini embeddings API не
      реализовывал — локального оказалось достаточно, а платить за
      каждый чанк смысла не было. `embeddings.py` — тонкий клиент
      поверх OpenAI-совместимого `/v1/embeddings`, с префиксами задачи
      (`search_document:`/`search_query:` — так модель обучена,
      без них хуже ранжирует). `start-embed-server.ps1` поднимает на
      `:8099`. **Грабли:** дефолтный `batch-size` сервера (512
      токенов) слишком мал для чанков ~1.5-2.5к символов — сервер падал
      с `input too large to process`; в скрипте `batch-size`/`ubatch-size`
      подняты до 4096.
- [x] Векторное хранение: BLOB (`float32.tobytes()`) в новой таблице
      `chunks`, брутфорс-косинус на numpy в `corpus.vector_search` —
      единственное исключение из stdlib-only, ROADMAP это и
      предполагал. На 38 чанках — мгновенно, sqlite-vec не понадобился.
- [x] Гибридный поиск: `corpus.hybrid_search` — RRF (k=60) поверх
      `search()` (BM25/FTS5, по works) и `vector_search()` (косинус, по
      chunks, свёрнуто до лучшего чанка на work). Деградирует до
      чистого BM25, если эмбеддинг-сервер не поднят или эмбеддингов ещё
      нет — не роняет вызывающий код, просто возвращает пустой
      векторный список.
- [x] `search_corpus` (агентский тул) переведён на `hybrid_search`
      вместо чистого BM25 — оба драйвера получили апгрейд бесплатно,
      код тулов трогать не пришлось.
- [x] `python research.py ask "вопрос"` — реализовано. **Отдельный
      тул `rag_query` для агента НЕ заводил** — сознательное отклонение
      от исходного пункта роадмапа: агент уже сам LLM в диалоге и может
      синтезировать ответ из результатов `search_corpus` в своём
      следующем сообщении, второй похожий тул только создавал бы
      путаницу выбора между двумя почти одинаковыми инструментами.
      `ask` — генерирует РЕАЛЬНЫЙ синтезированный ответ с цитатами
      одним вызовом DeepSeek, без agent-луп и без единого внешнего
      API-вызова; это качественно другая штука (готовый ответ, а не
      сырые хиты), поэтому и живёт отдельно от тула.
- [x] Автозапуск: `trace.py` в конце прогона best-effort чанкует+
      эмбеддит новые fulltexts (`RunTrace._try_embed_pending`) — не
      требует отдельного шага, но и не роняет прогон, если сервер не
      поднят.

**Сквозная проверка:** `python research.py ask "..."` на реальном
вопросе про RRF vs взвешенную сумму — нашёл релевантный чанк через
`hybrid_search`, DeepSeek синтезировал ответ с корректной цитатой [1],
ни одного внешнего API-вызова.

**Результат:** вопросы к накопленной библиотеке — секунды и почти
бесплатно.

## Фаза 3 — граф знаний (M–L) — done (2026-07-19, детерминированная часть)

- [x] Граф цитирований из OpenAlex — детерминированный, без LLM.
      `works.openalex_id` (новая колонка + ALTER-миграция для старых
      баз) и единая таблица рёбер `work_edges(kind, from_id, to_id)`
      — `kind='cites'` и `kind='related'` в одной схеме вместо двух
      похожих таблиц. `referenced_works` и **`related_works`**
      (OpenAlex сам считает topic/embedding-похожесть — не пришлось
      городить свою co-citation эвристику) идут в `select` бесплатно,
      вместе с обычным `search_openalex` — отдельного API-вызова не
      требуют. Отдельных таблиц под авторов/площадки/темы не заводил —
      `authors`/`venue` уже есть плоской строкой в `works` с Фазы 1,
      этого хватает; полноценный граф авторства не входил в объём.
- [x] Инструменты агента — **3, не 4-5, как в исходном пункте**:
  - `graph_cites(doi)` — что работа цитирует, из локальных рёбер,
    бесплатно и мгновенно.
  - `graph_related(doi)` — похожие работы по оценке OpenAlex, тоже
    локально и бесплатно.
  - `graph_cited_by(doi)` — кто цитирует работу, **живой** запрос
    `filter=cites:{id}` (в отличие от первых двух — стоит API-вызова),
    результаты сразу обогащают корпус (`ingest_openalex`) и добавляют
    рёбра `citing → seed` явно (не полагаясь на то, что seed обязательно
    попадёт в `referenced_works` цитирующей работы).
  - Все три принимают **DOI**, не внутренний `work_id` — это то, что
    агент и так видит в каждом результате `search_openalex`/
    `search_corpus`; резолвится в `openalex_id` внутри.
- [x] Retrieval через граф — реализован как явные тулы, а не
      автоматическое расширение внутри `hybrid_search`: агент сам
      решает, когда идти по графу, а не корпус решает это молча за
      него. Тесно связано с `search_corpus`/`CORPUS_HINT`, которые уже
      подталкивают агента искать локально перед внешними тулами.
- [ ] **Сознательно не делал** (по прямой инструкции самого роадмапа —
      «дорого, лениво, только если понадобится», «только если простого
      расширения перестанет хватать»):
      LLM-извлечение сущностей/триплетов, GraphRAG-сообщества и саммари,
      поиск путей между работами (граф пока слишком разрежен — 60 works,
      6 из них с рёбрами — path-finding по нему пока бессмысленен).

**Сквозная проверка (реальный прогон, не юнит-тест):** попросил агента
найти статью Bruch et al. и через `graph_cited_by` понять, куда
движется тема. Модель сама выстроила цепочку `search_corpus` →
`search_openalex` → `graph_cited_by(doi=..., limit=30)` и написала
содержательный ответ про эволюцию гибридного retrieval в сторону
RAG-пайплайнов, эффективности и доменной специализации — по 5 реальным
цитирующим работам 2023–2026. Корпус после этого: 60 works (было 55),
349 рёбер (289 cites + 60 related) из 6 работ с `openalex_id`.

**Результат:** ответы на вопросы «на чём основано», «кто это развил»
— работают. «Как связаны X и Y» (поиск путей) — отложено до фазы
роста графа, см. пункт выше.

## Фаза 4 — обвязка и интеграции (по частям, S каждая)

- [x] MCP-сервер поверх корпуса (2026-07-19) — `mcp_server.py`,
      JSON-RPC 2.0 по stdio (`initialize`/`tools/list`/`tools/call`/
      `ping`), реализован вручную — stdlib-only, без пакета `mcp`, тот
      же принцип, что и везде в проекте. 6 инструментов — read-
      поверхность корпуса: `search_corpus`, `ask_corpus` (переименован
      из плейсхолдера `rag_query` в исходном пункте — рифмуется с уже
      существующим `search_corpus`; переиспользует
      `research.synthesize_answer`, вынесенный рефакторингом из CLI-
      команды `ask`, без дублирования похода в DeepSeek), `graph_cites`,
      `graph_related`, `graph_cited_by`, `get_fulltext`. **Сознательно
      не включены** `search_openalex`/`search_core`/`search_brave` —
      те РАСТЯТ корпус (дело research.py/research_gemini.py), а не
      читают его; смешение ролей значило бы, что любой MCP-клиент
      может незаметно жечь лимиты Brave/CORE просто листая библиотеку.
      Зарегистрирован для обоих клиентов из исходного пункта —
      [.mcp.json](.mcp.json) (Claude Code) и [opencode.json](opencode.json)
      (opencode; формат сверен по официальной документации
      `opencode.ai/docs/mcp-servers`, не угадан по памяти — там
      `type: "local"` и `command` единым массивом, а не отдельные
      `command`+`args`, как у Claude Code).
      **Проверено вживую, не моком:** подпроцесс-тест гоняет реальный
      протокол — настоящий гибридный поиск по корпусу, настоящий граф
      цитирований (реальные рёбра по DOI `10.1145/3596512`), кэш-
      попадание `get_fulltext` (85692 символа, `cached: true`), один
      настоящий вызов DeepSeek через `ask_corpus` с цитатой `[1]` в
      ответе, плюс обработка плохих аргументов/неизвестного метода/
      неизвестного инструмента/битой JSON-строки без падения сервера.
      **Подхват клиентом проверен для Claude Code** (2026-07-19,
      `claude mcp list`/`get` изнутри репозитория): `.mcp.json`
      читается и парсится верно — scope "Project config", type stdio,
      command/args в точности как в файле. Статус
      `⏸ Pending approval (run 'claude' to approve)` — это штатный
      one-time trust-gate Claude Code для project-scoped серверов
      (иначе любой открытый репозиторий мог бы незаметно зарегистрировать
      автозапускаемую команду), а не баг и не недоделанная регистрация.
      Проверено также, что это НЕ обходится не-интерактивно: ни
      `claude -p "..." --no-session-persistence` (доки прямо говорят,
      что trust-диалог в print-режиме "skipped", но проверка `mcp list`
      после запуска показала статус всё тем же Pending — bypass
      одноразовый, ничего не сохраняет в проектный стейт), ни
      `claude doctor` (по докам спавнит stdio-серверы из .mcp.json для
      health-check, но оказался интерактивным TUI-дашбордом, который не
      завершается сам в неинтерактивном контексте — убит вручную).

      **Поправка:** первоначальный вывод («это осознанный
      security-boundary, а не баг») оказался неверным — три подряд
      реальных интерактивных подтверждения пользователя НЕ проставили
      `hasTrustDialogAccepted`/`enabledMcpjsonServers` в `~/.claude.json`
      (перепроверено напрямую чтением файла между попытками, не только
      через `claude mcp list`). Нашёлся через WebSearch/WebFetch (а не
      гадание — по прямой обратной связи от пользователя): это известный
      баг, специфичный для Windows — диалог approval для project-scoped
      MCP-серверов иногда не всплывает вообще (GitHub issues
      [#9189](https://github.com/anthropics/claude-code/issues/9189),
      [#13389](https://github.com/anthropics/claude-code/issues/13389),
      второй — репро именно на Windows). Официальные доки
      (`code.claude.com/docs/en/mcp`) это подтверждают отдельным
      абзацем и дают версионированный обходной путь: до v2.1.207
      (стоит v2.1.202) неотслеживаемый `.claude/settings.local.json` с
      `enabledMcpjsonServers` одобряет сервер даже в «недоверенной»
      папке, без прохождения trust-диалога вообще. Применено:
      `.claude/settings.local.json` (в `.gitignore` — именно
      неотслеживаемость файла и есть условие, при котором это
      работает) с `{"enabledMcpjsonServers": ["research-engine"]}`.
      **Проверено вживую:** `claude mcp list`/`get` после этого
      показывают `research-engine: ... - ✔ Connected` (реальный
      health-check запускается при каждом вызове `mcp list`, не
      кэш).

      **Сквозная проверка до конца цепочки** (2026-07-19,
      `claude -p ... --output-format stream-json` из `research-engine`):
      свежая сессия видит все 6 `mcp__research-engine__*` в списке
      инструментов при старте, сама через `ToolSearch` подгружает схему
      `search_corpus`, вызывает его с реальным запросом и получает
      реальный результат из `corpus.db` (та же статья Bruch et al.,
      что и в проверке Фазы 1/3) — `permission_denials: []`. Это
      закрывает последнее непроверенное звено всей цепочки MCP-сервера:
      от stdio-протокола (Фаза 4, подпроцесс-тест) до живой сессии
      Claude Code, вызывающей инструмент и получающей настоящие данные.
      opencode-сторона (`opencode.json`) тем же способом не
      перепроверялась — там свой клиент и свой флоу доверия.
- [ ] Мультимодельность: `research_gemini.py` уже даёт второй драйвер

Репозиторий опубликован на GitHub —

публичный, для использования в портфолио на собеседованиях. Перед
публикацией — реальная проверка безопасности, не формальная: pickaxe-
поиск (`git log --all -S"<префикс ключа>"`) по всей истории на каждый
реальный секрет из `secrets.json`, ни один нигде не засветился.
`README.md` стал двуязычным (английская секция сверху — питч,
архитектура, инженерные хайлайты; русская секция ниже — исходная и
осталась авторитетной). Участие Claude Code в разработке — открыто,
как факт (сознательное решение, не default): `Co-Authored-By` уже есть
в каждом коммите, скрывать было бы нечестно, а для многих интервьюеров
сейчас это прямой плюс. Добавлена MIT LICENSE.

`docs/demo.gif` — демонстрация `research.py ask` для README. Пробовал
буквальную запись экрана — не сработало ни технически, ни по существу:
процессы, которыми управляет агент, не рендерятся ни в каком видимом
окне на рабочем столе пользователя, а захват `gdigrab desktop`
буквально показал реальный рабочий стол (открытый YouTube, личные
вкладки браузера) — публиковать такое в README нельзя. Вместо этого —
`docs/make_demo_gif.py` (Pillow, шрифт Consolas): рендерит
терминал-стиль анимацию из **реально захваченного** вывода настоящего
прогона `research.py ask` (вопрос подобран заранее — проверил
retrieval бесплатным вызовом `corpus.hybrid_search` до траты реального
вызова DeepSeek, чтобы не жечь API-запросы на неудачные попытки).
Тот же принцип, что у `asciinema`/`vhs` — записывать реальный
терминальный ввод-вывод, а не пиксели экрана; ни `asciinema`, ни `vhs`
не были установлены, поэтому написан свой минимальный рендерер.
Грабли по пути: общая палитра GIF из adaptive quantization одного
кадра теряла цвета мелких элементов (точки псевдо-«светофора» в шапке
окна, которые занимают мало пикселей) — исправлено явной палитрой,
собранной из ровно тех цветов, что реально используются.

## Риски и ограничения

- Лимиты API: Brave free — 1 rps и месячный потолок; CORE — щадящие
  лимиты. Кэш и `search_corpus` прямо на это работают.
- sqlite3 в питоне на Windows: FTS5 в официальных сборках есть,
  а вот загрузка расширений (sqlite-vec) может быть выключена —
  поэтому базовый путь для векторов: numpy-брутфорс.
- Качество LLM-извлечения сущностей нестабильно → сначала
  детерминированный граф цитирований, LLM-триплеты — вторым шагом.
- Кодировки Windows: везде явный `encoding="utf-8"` (уже так).

## Порядок

0 → 1 → 2 → 3; фаза 4 — по мере надобности, её пункты независимы.
Первая осмысленная веха — конец фазы 1: агент с памятью, которая
не протухает между запусками. **Достигнута 2026-07-19.**

Фаза 2 тоже закрыта 2026-07-19 — выбор пал на локальные эмбеддинги
(`nomic-embed-text-v1.5` через `llama-server`, см. Фазу 2 выше);
Gemini embeddings API не реализовывался.

Фаза 3 закрыта 2026-07-19 в детерминированной части (граф цитирований
из OpenAlex, три тула). LLM-извлечение сущностей, GraphRAG-сообщества
и path-finding между работами — сознательно отложены, роадмап сам об
этом просил («дорого, лениво», «только если понадобится»); граф пока
и физически слишком маленький (60 works, 6 с рёбрами) для path-finding.

Все четыре фазы из исходного плана прожиты. Дальше — либо копить
данные обычным использованием (граф и корпус растут сами по себе с
каждым прогоном) и возвращаться к отложенным пунктам, когда они
реально понадобятся, либо переходить к Фазе 4 (обвязка/интеграции,
её пункты независимы и не требуют строгого порядка).

Фаза 4 начата и наполовину сдвинута 2026-07-19: первый пункт
(MCP-сервер) закрыт в тот же день, детали выше. Заодно всплыл приятный
побочный факт: корпус успел органически подрасти между сессиями (88
works, 1512 рёбер на момент теста — было 60/349 сразу после Фазы 3) —
не гипотеза из предыдущего абзаца, а уже наблюдаемое поведение.
Остальные три пункта Фазы 4 (мультимодельность через OmniRoute,
инкрементальные обзоры, цитаты на уровне чанков) не начаты — независимы
друг от друга и от MCP-сервера, браться можно в любом порядке по мере
надобности.
