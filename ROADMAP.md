# ROADMAP — план развития research-engine

## Видение

Из одноразового агента («промпт → отчёт») — в исследовательскую систему
с накапливаемым корпусом: каждый запуск обогащает локальную базу
источников, по которой можно искать и отвечать на вопросы (RAG) без
повторных походов во внешние API, а поверх — граф знаний (цитирования,
сущности, связи между работами).

## Принципы

- Минимум зависимостей: stdlib + SQLite; numpy и расширения — только
  когда без них никак.
- CPU-only friendly: эмбеддинги через локальный llama.cpp
  (`--embedding`) или бесплатные API; никаких тяжёлых ML-стеков.
- Бережём бюджеты API (Brave free 1 rps, CORE, DeepSeek) — локальный
  кэш обязателен.
- Всё состояние — один файл SQLite (`corpus.db`): просто бэкапить,
  просто смотреть глазами.

## Внеплановое: DeepSeek vs Gemini (2026-07-19)

Второй драйвер (`research_gemini.py`, Gemini 3.5 Flash через Interactions
API) появился раньше Фазы 4 — по прямому запросу, не по плану. Прогнали
обе модели на двух реальных темах из Фазы 2/3 (гибридный ретривал,
citation-graph retrieval) с одинаковым набором инструментов. Разбор —
[comparisons/2026-07-19-deepseek-vs-gemini/SUMMARY.md](comparisons/2026-07-19-deepseek-vs-gemini/SUMMARY.md).
Коротко: DeepSeek глубже и охотнее лезет в OpenAlex/CORE, но дороже и
медленнее; Gemini компактнее и в моменте бесплатен, но почти не трогал
специализированные научные инструменты и упирается в free-tier rate
limit быстрее. Встроенный `google_search` не взлетел без биллинга —
подробности там же.

Следом прогнали весь доступный зоопарк моделей Gemini (7 вариантов) —
сначала на одной теме, потом (после того как в `research_gemini.py`
починили обрезку текста ошибки до 300 символов) повторили на второй —
картина идентична на обеих, разбор в
[comparisons/2026-07-19-gemini-model-zoo/SUMMARY.md](comparisons/2026-07-19-gemini-model-zoo/SUMMARY.md).
Из семи реально отработали три, и все — Flash: `gemini-3.5-flash`,
`gemini-3.1-flash-lite`, `gemini-3-flash-preview`. Оба Pro-варианта
упёрлись в `429` на обеих темах — с полным текстом ошибки выяснилось,
что это не рейт-лимит, а буквально `limit: 0` на free tier для Pro,
подтверждено самим API. `gemini-2.5-flash`/`-flash-lite` сняты с
публичного доступа, `gemini-2.0-flash` стабильно валит `500` через
новый Interactions API (старое поколение с ним, похоже, несовместимо) —
оба факта не зависят от темы. Из рабочих младших моделей ни
`3.1-flash-lite`, ни `3-flash-preview` не позвали ни одного инструмента
ни на одной из двух тем — и на второй теме `3.1-flash-lite` поймана на
галлюцинированной ссылке (реальный DOI, но статья о совершенно другом).
Для research-агента вывод устойчивый: `gemini-3.5-flash` пока
единственный реально пригодный вариант в этой линейке на бесплатном
ключе — остальные Flash-варианты дешевле, но менее надёжны, не просто
компактнее.

## Фаза 1 — корпус (M; ключевая — всё дальнейшее стоит на ней) — done (2026-07-19)

`corpus.db` (SQLite, `corpus.py`):

- [x] `works` — работы из OpenAlex/CORE/Brave, дедуп по DOI/core_id/URL
      (свежие непустые поля побеждают старые при повторной встрече).
      **Известный пробел:** дедуп только по точным идентификаторам, без
      fuzzy-match по заголовку — если CORE не вернул DOI для записи,
      которая уже есть по OpenAlex, получится дубль-строка (наблюдал
      это на «An Analysis of Fusion Functions for Hybrid Retrieval» —
      DOI у OpenAlex-версии есть, у CORE-версии в ответе поиска не
      пришёл). Не чиню — не входило в объём фазы, fuzzy-дедуп заведёт
      риск ложного слияния разных работ.
- [x] `fulltexts` — кэш полных текстов CORE, `get_fulltext` сначала
      смотрит сюда (подтверждено: второй запрос того же core_id вернул
      `cached: true`, без похода в CORE API).
- [x] `runs` — пишет `trace.py` при старте/финише запуска (провайдер,
      модель, usage, раунды). Отдельную `tool_calls`-таблицу в SQLite
      не заводил — тот же смысл уже даёт `runs/<run_id>/tool_calls.jsonl`
      на диске, дублировать в БД не стал (не ради красоты).
- [x] FTS5-индекс (`works_fts`, `tokenize=unicode61`) по title/abstract/
      description/fulltext, ранжирование через `bm25()`. Риск из раздела
      «Риски» не подтвердился — FTS5 в этой сборке `sqlite3` (3.49.1)
      работает из коробки, включая кириллицу.

Новый инструмент агента `search_corpus` — в `TOOL_SPECS`, автоматически
доступен обоим драйверам. Промпт агента получает `CORPUS_HINT`
(«сначала проверь корпус») — работает: в тестовом прогоне модель сама
трижды дёрнула `search_corpus` первым делом.

**Сквозная проверка (реальная, не синтетика):** прогнал тему A через
`research.py` (DeepSeek) — корпус наполнился 48 работами (29 brave / 16
openalex / 3 core) + 1 закэшированный фултекст. Затем **отдельным
процессом**, через **другой драйвер** (`research_gemini.py`), с
**другой формулировкой** запроса — Gemini сам нашёл ту же статью через
`search_corpus` и получил её текст через `get_fulltext` с `cached: true`.
Корпус реально переживает между прогонами и между провайдерами — не
только в теории.

Заодно чинил реальный баг, не связанный с корпусом напрямую: `print()`
падал на кириллице в аргументах тул-коллов из-за не-UTF8 консоли
Windows (`sys.stdout.reconfigure` в обоих драйверах).

**Результат:** «RAG-лайт» без эмбеддингов уже работает — полнотекстовый
поиск по накопленному.

## Фаза 2 — RAG (M) — done (2026-07-19)

- [x] Чанкинг фултекстов (`chunking.py`): по абзацам (`\n\s*\n`),
      target 1500 / max 2200 символов, рекурсивный фолбэк по границам
      предложений для абзацев крупнее max. Без overlap — границы по
      абзацам и так сохраняют смысловые единицы. Offsets точные
      (проверено побайтово на реальном фултексте: 85 692 символа → 38
      чанков, все `text[start:end] == chunk.text`). На редких абзацах
      без знаков препинания (списки литературы, формулы) может
      перебрать max на ~15% — не чинил, не критично для эмбеддинга.
- [x] Эмбеддинги — выбрал **локальный путь**: `llama-server --embedding`
      + `nomic-embed-text-v1.5` (уже была скачана для LM Studio,
      768 измерений, мультиязычная). Gemini embeddings API не
      реализовывал — локального оказалось достаточно, а платить за
      каждый чанк смысла не было. `embeddings.py` — тонкий клиент
      поверх OpenAI-совместимого `/v1/embeddings`, с префиксами задачи
      (`search_document:`/`search_query:` — так модель обучена,
      без них хуже ранжирует). `start-embed-server.ps1` поднимает на
      `:8099`. **Грабли:** дефолтный `batch-size` сервера (512
      токенов) слишком мал для чанков ~1.5-2.5к символов — сервер падал
      с `input too large to process`; в скрипте `batch-size`/`ubatch-size`
      подняты до 4096.
- [x] Векторное хранение: BLOB (`float32.tobytes()`) в новой таблице
      `chunks`, брутфорс-косинус на numpy в `corpus.vector_search` —
      единственное исключение из stdlib-only, ROADMAP это и
      предполагал. На 38 чанках — мгновенно, sqlite-vec не понадобился.
- [x] Гибридный поиск: `corpus.hybrid_search` — RRF (k=60) поверх
      `search()` (BM25/FTS5, по works) и `vector_search()` (косинус, по
      chunks, свёрнуто до лучшего чанка на work). Деградирует до
      чистого BM25, если эмбеддинг-сервер не поднят или эмбеддингов ещё
      нет — не роняет вызывающий код, просто возвращает пустой
      векторный список.
- [x] `search_corpus` (агентский тул) переведён на `hybrid_search`
      вместо чистого BM25 — оба драйвера получили апгрейд бесплатно,
      код тулов трогать не пришлось.
- [x] `python research.py ask "вопрос"` — реализовано. **Отдельный
      тул `rag_query` для агента НЕ заводил** — сознательное отклонение
      от исходного пункта роадмапа: агент уже сам LLM в диалоге и может
      синтезировать ответ из результатов `search_corpus` в своём
      следующем сообщении, второй похожий тул только создавал бы
      путаницу выбора между двумя почти одинаковыми инструментами.
      `ask` — генерирует РЕАЛЬНЫЙ синтезированный ответ с цитатами
      одним вызовом DeepSeek, без agent-луп и без единого внешнего
      API-вызова; это качественно другая штука (готовый ответ, а не
      сырые хиты), поэтому и живёт отдельно от тула.
- [x] Автозапуск: `trace.py` в конце прогона best-effort чанкует+
      эмбеддит новые fulltexts (`RunTrace._try_embed_pending`) — не
      требует отдельного шага, но и не роняет прогон, если сервер не
      поднят.

**Сквозная проверка:** `python research.py ask "..."` на реальном
вопросе про RRF vs взвешенную сумму — нашёл релевантный чанк через
`hybrid_search`, DeepSeek синтезировал ответ с корректной цитатой [1],
ни одного внешнего API-вызова.

**Результат:** вопросы к накопленной библиотеке — секунды и почти
бесплатно.

## Фаза 3 — граф знаний (M–L)

- Граф цитирований из OpenAlex — детерминированный и без LLM: у работ
  есть `referenced_works`, обратные ссылки — `filter=cites:W…`.
  Таблицы рёбер work→work, авторы, площадки, темы (topics OpenAlex).
- Retrieval через граф: «найди сиды текстовым поиском → расширь по
  цитированиям в обе стороны» — так достаются работы, которые
  текстовый поиск не находит.
- Извлечение сущностей/утверждений (DeepSeek по фултекстам из кэша):
  методы, модели, датасеты, метрики, результаты → триплеты в SQLite.
  Дорого — делать лениво и по запросу.
- Инструменты агента: `cites` / `cited_by` / `related(work_id)`,
  поиск путей между работами.
- GraphRAG с сообществами и саммари — только если простого расширения
  по цитированиям перестанет хватать.

**Результат:** ответы на вопросы «на чём основано», «кто это развил»,
«как связаны X и Y».

## Фаза 4 — обвязка и интеграции (по частям, S каждая)

- MCP-сервер поверх корпуса (`search_corpus` / `rag_query` / граф) —
  чтобы Claude Code и opencode ходили в библиотеку напрямую.
- Мультимодельность: `research_gemini.py` уже даёт второй драйвер
  напрямую (см. «Внеплановое» выше); ещё один путь на будущее — base_url
  в конфиг → OmniRoute (:20128) как бесплатная альтернатива без похода
  во внешние API напрямую.
- Инкрементальные обзоры: «что нового по теме X с прошлого запуска»
  (фильтр по датам публикаций + дифф корпуса).
- Отчёты с цитатами, указывающими на конкретные чанки корпуса.

## Риски и ограничения

- Лимиты API: Brave free — 1 rps и месячный потолок; CORE — щадящие
  лимиты. Кэш и `search_corpus` прямо на это работают.
- sqlite3 в питоне на Windows: FTS5 в официальных сборках есть,
  а вот загрузка расширений (sqlite-vec) может быть выключена —
  поэтому базовый путь для векторов: numpy-брутфорс.
- Качество LLM-извлечения сущностей нестабильно → сначала
  детерминированный граф цитирований, LLM-триплеты — вторым шагом.
- Кодировки Windows: везде явный `encoding="utf-8"` (уже так).
