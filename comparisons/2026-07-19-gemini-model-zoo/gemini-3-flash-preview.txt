Гибридный поиск (BM25 + Vector) — это «золотой стандарт» для RAG, так как он объединяет точность терминологии (BM25) с семантическим пониманием (embeddings). Ниже представлен разбор вашей архитектуры.

## 1. Актуальные практики гибридного поиска и слияние скоров

Основная проблема гибридного поиска — разная природа шкал: BM25 не ограничен сверху, а косинусное сходство лежит в диапазоне [0, 1].

**Reciprocal Rank Fusion (RRF)** остается самым популярным методом. Он не требует нормализации скоров, так как опирается только на позицию документа в результатах. Формула: `score = sum(1 / (k + rank))`, где `k` (обычно 60) сглаживает влияние низких рангов. RRF надежен, но его минус — невозможность «подкрутить» важность одного из методов.

**Альтернативы:**
— **Weighted Convex Combination:** `score = alpha * normalized_bm25 + (1 - alpha) * vector_score`. Требует предварительной нормализации (Min-Max или Sigmoid). Позволяет выставить приоритет, например, `alpha=0.3` для научного поиска, где семантика важнее точных совпадений слов.
— **Cross-Encoder Re-ranking:** использование тяжелой модели (например, BGE-Reranker) для переранжирования топ-50 результатов гибридного поиска. Это дает максимальную точность, нивелируя недостатки первичного скоринга.

**Проблемы на практике:** «Размывание» результатов. Если BM25 находит точный термин, а векторный поиск — общие по смыслу, но бесполезные статьи, RRF может поднять мусор выше релевантного ответа.

## 2. Brute-force на CPU: когда это перестает работать

Для десятков тысяч чанков (например, 50 000 векторов по 768 измерений) brute-force на NumPy — абсолютно адекватное решение.

**Производительность:**
— Матрица 50,000 x 768 (float32) занимает около 150 МБ RAM.
— Операция `dot(matrix, query_vector)` на современном CPU занимает 5–15 мс. Это быстрее, чем сетевой запрос к внешней БД.

**Подводные камни:**
— **Деградация при росте:** Проблемы начнутся на 200–500 тысячах векторов. Линейный поиск `O(N)` начнет занимать >100 мс, что критично для отзывчивости.
— **Типы данных:** Если использовать `BLOB` в SQLite, основное время будет уходить на десериализацию данных из БД в массив NumPy.
— **Когда переходить на расширения:** Если нужно делать фильтрацию (например, поиск только по статьям 2023 года) одновременно с векторным поиском, лучше взять `sqlite-vec`. Оно позволяет делать векторный поиск прямо в SQL-запросе, эффективно совмещая его с `WHERE`-фильтрами.

## 3. Рекомендации по чанкам для научных статей

Научные тексты отличаются высокой плотностью информации и сложной структурой.

— **Размер чанка:** Оптимально 400–600 токенов (примерно 2000–3000 символов). Слишком мелкие чанки (100 токенов) теряют контекст доказательств, слишком крупные (1000+) «размывают» эмбеддинг, делая его слишком общим.
— **Перекрытие (Overlap):** 10–20% (50–100 токенов). Это критично для сохранения связи между абзацами, особенно в секциях Methodology и Results.
— **Структурный подход:** Для научных статей лучше использовать не просто разбиение по символам, а `RecursiveCharacterTextSplitter` с приоритетом на двойные переносы строк (абзацы) и точки. В идеале — сохранять метаданные (название секции, авторы) в каждом чанке.

## 4. Рекомендуемые источники

1. **Статья "Using Binary Quantization to retrieve millions of documents" (Hugging Face Blog).** Описывает, как сжатие векторов и простой точечный поиск работают на практике. Полезно для понимания лимитов CPU.
2. **Репозиторий `asg017/sqlite-vec`.** Самое актуальное расширение для векторного поиска в SQLite от автора `sqlite-vss`. Оно написано на C, чрезвычайно быстрое и идеально подходит для локального RAG.
3. **Документация Weaviate / Pinecone по Hybrid Search.** У них лучшие разборы того, почему RRF часто выигрывает у взвешенного суммирования и как настраивать веса.
4. **Статья "Prendu: Reciprocal Rank Fusion" (Medium/блоги разработчиков).** Математическое и практическое обоснование того, почему константа `k=60` является стандартом де-факто.

**Итог для вашего случая:** Пока у вас <100к чанков, связка SQLite (FTS5) + NumPy (для векторов) — самое простое и производительное решение. Используйте RRF для слияния, но добавьте нормализацию и Cross-Encoder, если почувствуете, что качество ответов падает.
