# Зачем вообще нужен research-engine: реальная цена делегирования исследования

Дата: 2026-07-19. Исходный мотив всего проекта (не задокументированный явно раньше) —
экономия квоты Claude: вместо того чтобы Claude Code сам тратил токены на
объёмные исследовательские задачи, эта работа делегируется дешёвому внешнему
драйверу (DeepSeek). Этот прогон — первая прямая проверка, во сколько это
реально обходится, не на словах.

**Тема выбрана заново**, не переиспользована из прошлых сравнений —
speculative decoding для инференса LLM, ноль пересечения с уже накопленным
корпусом (проверено `corpus.hybrid_search` до старта: единственное совпадение
имело rrf-score 0.016, шум). Всем трём прогонам дан **один и тот же** промпт —
[prompt_speculative_decoding.txt](prompt_speculative_decoding.txt).

## Три прогона, не два

- **research.py (DeepSeek)** — обычный агентский цикл проекта.
- **Claude, естественное поведение** — `claude -p` из нейтральной директории
  (не внутри research-engine, без контекста этого проекта), тот же промпт,
  без ограничений на инструменты кроме бюджетного потолка. Claude Code сам
  решил, как исследовать тему.
- **Claude, с ограничением** — то же самое, но с `--disallowedTools Skill`,
  чтобы увидеть более скромный сценарий без эскалации в тяжёлый навык.

## Числа

| | research.py (DeepSeek) | Claude (без Skill) | Claude (естественно) |
|---|---|---|---|
| Раундов/turns | 5 | 9 | 10 |
| Вызовов инструментов | 10 | 8 (1 ToolSearch + 7 WebSearch) | 9 видимых (2 Skill + 1 ToolSearch + 6 WebSearch — реальные саб-агенты внутри Skill не видны на этом уровне) |
| Какие инструменты | search_corpus, search_openalex, search_brave, search_core, graph_cited_by | WebSearch/WebFetch (общий веб) | Skill `deep-research` (fan-out + верификация) поверх WebSearch/WebFetch |
| Токены (видимые) | 37 862 prompt + 3 343 completion | 2 487 + 27 823 cache-write + 145 380 cache-read + 3 669 output | 11 + 99 882 cache-write + 183 269 cache-read + 5 780 output |
| **Реальная цена** | **≈ $0.0194** | **$0.446** | **$0.895** |
| Во сколько раз дороже DeepSeek | 1× (база) | **≈ 23×** | **≈ 46×** |
| Время (wall-clock) | 70 с | 65 с | 96 с |

Цена DeepSeek посчитана по прайсу (`$0.435`/`$0.87` за 1M input/output,
см. [сравнение DeepSeek vs Gemini](../2026-07-19-deepseek-vs-gemini/SUMMARY.md)
— прайс от того же дня, актуален). Цена Claude — **не пересчитана вручную**,
взята как есть из `total_cost_usd`, который возвращает сам харнесс. Пробовал
разложить её по табличным ставкам ($2/$10 за 1M input/output intro-цена
Sonnet 5, 0.1× за cache-read, 1.25× за cache-write) — получилось заметно
меньше реальной цифры в обоих случаях (≈$0.25 расчётных против $0.55
реальных на ограниченном прогоне, ≈$0.34 против $0.89 на естественном).
Не стал выдавать это за объяснённое — скорее всего, часть цены — это сам
`WebSearch` как отдельно тарифицируемый server-tool (аналогично тому, как
устроен code execution), и/или расходы саб-агентов `deep-research`, не
попадающие в верхнеуровневый `usage`. Честнее показать реальное число, чем
выдать неполную реконструкцию за полную.

## Реальная методологическая ловушка, о которую сам споткнулся

Первая попытка «ограниченного» прогона (`--disallowedTools Skill` без
`--allowedTools`) тихо провалилась: все три вызова `WebSearch` вернулись с
`"Claude requested permissions to use WebSearch, but you haven't granted it
yet"` — в неинтерактивном `-p`-режиме подтвердить разрешение некому, и
вместо ошибки получаешь молчаливый отказ. Модель это заметила и честно
написала в конце отчёта: «у меня не было доступа к веб-поиску... ссылки
приведены по памяти» — не стала скрывать. Но для чистоты сравнения это
значит, что первый прогон был не «Claude ищет дёшево», а «Claude отвечает
по памяти с проваленными вызовами инструментов» — не то, что нужно было
измерить. Перезапустил с явным `--allowedTools "WebSearch,WebFetch"` —
7 реальных поисковых вызовов, 0 отказов, реальные URL в результатах
(проверено по сырому `stream-json`, не на слово). Числа выше — уже из
исправленного прогона.

## Качество отчётов

Прочитал все три полностью — [research_engine_output.txt](research_engine_output.txt),
[claude_native_constrained.txt](claude_native_constrained.txt),
[claude_native_unconstrained.txt](claude_native_unconstrained.txt).

- **Покрытие методов идентично** во всех трёх: оригинальный speculative
  decoding (Leviathan/Chen), Medusa, EAGLE/EAGLE-2(/-3), Lookahead decoding —
  ни один прогон не пропустил и не выдумал лишний метод.
- **Цитаты сходятся** — все три независимо называют одни и те же arXiv ID
  (2211.17192, 2302.01318, 2401.10774, 2401.15077, 2402.02057 и т.д.).
  Три независимых процесса, сошедшихся на одинаковых идентификаторах —
  сильный сигнал, что это реальные, а не галлюцинированные работы;
  отдельно по DOI не перепроверял (не было ключевой находки, которая бы
  это потребовала, в отличие от сравнения DeepSeek/Gemini ранее).
- **DeepSeek нашёл то, чего не было ни у одного Claude-прогона**: что
  multi-token prediction (MTP) — встроенный speculative decoding без
  второй модели — уже есть «из коробки» в DeepSeek-V3 и Qwen 3.6,
  поддержан в llama.cpp напрямую. Специфичная, точная деталь на стыке
  собственных знаний модели о её архитектуре и веб-поиска.
- **Claude-прогоны детальнее в цифрах** — например, EAGLE-2 «на 20–40%
  быстрее EAGLE-1» вместо просто диапазона ускорения; естественный
  прогон нашёл живое GitHub-обсуждение (issue #15902) о добавлении
  EAGLE-3 в llama.cpp — конкретное, свежее, проверяемое.
- Ни у одной из трёх версий не поймал явной фабрикации при чтении — но
  это не полноценный аудит, а как и в прошлый раз (см. сравнение
  DeepSeek/Gemini) — ориентир, не доказательство отсутствия галлюцинаций.

## Вывод

Исходный мотив подтверждается количественно, не только интуитивно:
делегирование одного и того же исследовательского запроса research.py
(DeepSeek) стоит **в 23–46 раз дешевле**, чем тот же запрос напрямую
через Claude Code — даже в лучшем для Claude случае (без эскалации в
тяжёлый навык), и даже с учётом того, что у research.py есть специализированные
научные источники (OpenAlex, CORE), которых у голого Claude-запроса нет.
Качество не деградирует пропорционально цене — все три отчёта одного
уровня содержательности, у каждого свои сильные детали, ни один явно не
хуже. Отдельная находка не про цену: естественное поведение Claude Code
на открытый исследовательский запрос — не «пара WebSearch-вызовов», а
автоматическая эскалация в собственный навык `deep-research` (fan-out +
верификация), что почти удваивает цену относительно контролируемого
сценария — сам этот выбор модели и есть часть той стоимости, которую
research-engine обходит.

Одна тема — ориентир, не бенчмарк; повторить на 2-3 разных доменах
(не только ML-систем), если понадобится более твёрдая оценка.
