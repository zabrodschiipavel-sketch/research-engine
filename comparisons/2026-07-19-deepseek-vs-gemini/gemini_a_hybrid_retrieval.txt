## 1. Актуальные практики гибридного поиска (BM25 + dense retrieval)

Для объединения результатов лексического (BM25) и семантического (векторного) поиска применяют два основных подхода:

*   **Score Fusion (слияние оценок):** Линейная комбинация нормализованных скоров ($S_{hybrid} = \alpha \cdot S_{dense} + (1-\alpha) \cdot S_{sparse}$). Главная проблема — разный масштаб. BM25 не ограничен сверху (может быть 0..30+), а косинусное сходство векторов обычно лежит в диапазоне $[0.6, 0.95]$. Нормализация (например, MinMax) крайне чувствительна к аномалиям (outliers): один документ с аномально высоким BM25-скором сожмет оценки остальных документов до нуля. Также требуется ручной подбор веса $\alpha$.
*   **Rank Fusion (слияние рангов / RRF):** Доминирующий промышленный стандарт. Оценка документа рассчитывается только на основе его позиций в выдаче обоих алгоритмов: $RRF(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$, где $r_m(d)$ — ранг документа в поиске $m$, а $k \approx 60$ — сглаживающая константа. RRF не зависит от масштабов скоров, стабилен и не требует калибровки.

**Альтернативы RRF:**
*   **Cross-Encoder (Reranking):** Извлечение top-N результатов (например, по 50 кандидатов из BM25 и векторного поиска) и их последующая переранжировка тяжелой нейросетью. Дает максимальное качество, но требует GPU-ресурсов.

**Проблемы на практике:**
Без последующей переранжировки (Reranking) гибридный поиск часто поднимает наверх нерелевантные документы из-за «голосов» одного из поисковиков (например, когда векторный поиск находит семантически похожий, но фактически неверный чанк, а RRF необоснованно высоко его оценивает).

## 2. Brute-force поиск на CPU в SQLite: подводные камни

Полнотекстовый brute-force (K-NN) на NumPy (через векторное умножение матриц) жизнеспособен при объеме до **50–100 тысяч векторов** (при размерности 384–768). NumPy использует под капотом высокооптимизированные библиотеки BLAS (MKL/OpenBLAS), что позволяет выполнять миллионы операций скалярного произведения за десятки миллисекунд.

**Подводные камни:**
1.  **Сериализация БД (главный bottleneck):** Постраничное чтение десятков тысяч BLOB-векторов из SQLite на каждый запрос в Python сводит на нет всю скорость NumPy. **Решение:** кэшировать всю матрицу эмбеддингов в оперативной памяти (RAM) при старте приложения, а в SQLite хранить только ID чанков.
2.  **Потребление RAM:** Матрица $50\,000 \times 768$ (float32) занимает около 150 МБ. Для локального RAG это допустимо, но на слабых машинах лимиты памяти критичны.
3.  **Масштабируемость:** С ростом базы время поиска растет линейно ($O(N)$). При $N > 100k$ задержка (latency) превысит 100 мс.

**Когда переходить на альтернативы:**
*   **sqlite-vec:** Стоит взять, если хочется оставить поиск внутри SQLite без оверхеда Python. Написан на C, работает быстрее связки Python+NumPy за счет отсутствия копирования данных из БД в интерпретатор. Поддерживает квантование (например, 1-bit / int8).
*   **FAISS / USearch / HNSWLIB:** Когда размер базы превышает 100k чанков, требуется суб-миллисекундный поиск (ANN) и есть свободная RAM под граф HNSW.

## 3. Размер чанка для научных статей

Научные статьи отличаются высокой плотностью терминов, формул, таблиц и перекрестных ссылок.

*   **Оптимальный размер:** **384–512 токенов** (примерно 1200–2000 символов). Меньший размер (<200) разрушает контекст доказательств, обрывает формулы и лишает вектор семантической полноты. Больший размер (>1000) размывает вектор представления («вектор обо всем»), снижая точность векторного поиска.
*   **Перекрытие (Overlap):** **64–128 токенов** (15–25%). Важно для сохранения непрерывности мысли, чтобы формулы или цитаты, оказавшиеся на границе, не терялись при ретривале.
*   **Стратегия нарезки:** Использовать **Recursive Character Splitter** (с приоритетом разделения по заголовкам разделов, параграфам `\n\n`, затем точкам) вместо жесткого деления по токенам. Крайне важно сохранять метаданные (название секции: Abstract, Methodology) внутри текста каждого чанка для точной работы BM25.
